# Рабочий запуск Wordli

Порядок первоначального запуска и последующих обновлений игры. Документ
сам по себе не разрешает merge, push, миграцию рабочей БД или перезапуск.
Для каждого релиза отдельно согласуют изменения и службы: только Copilot
и игровой API, без перезапуска VPS, БД и других ботов.

## Разделение служб

```text
Telegram → https://copilot-games-v4956.duckdns.org
                         ↓ HTTPS proxy на VPS
                 127.0.0.1:8770 → wordliapi → PostgreSQL
```

- HTML/CSS/JS и API находятся на одном origin, без CORS и GitHub Pages.
- `production_server` — HTTP-сервер, а не второй polling основного бота.
- HTTPS-proxy управляется отдельно от приложения. Он не открывает порт БД.
- `docker-compose.wordli.yml` содержит только игру. Не объединять его
  запуск с безусловным `up`, `down` или `restart` всего основного Compose.
- В рабочей БД используются только `wordli_profiles`, `wordli_requests`
  и `wordli_settings` (публичное имя, часовой пояс, добровольные напоминания).
  Таблицы `users`, `games`, `payments` и `cookbook` не меняются.
- В production нет автоматического DDL, seed или импорта тестовой SQLite.
- Тестовый entrypoint сохраняет прежние ограничения и не подходит для
  production. Не обходить их запуском рабочего бота с `APP_ENV=test`.

## Образ и зависимости

`Dockerfile.wordli` копирует только игровую папку и конфигурационный модуль,
не устанавливает aiogram, numpy и инструменты подготовки словаря.
`requirements-wordli.txt` отдельно фиксирует HTTP-зависимости, включая
`aiohttp==3.14.5`. Основной бот остаётся на собственном requirements.
Атрибуция, лицензии, готовый словарь и его архив находятся внутри образа.

До передачи образа проверяют отсутствие секретов и тестовых файлов,
сохраняют старый image ID, выбирают неизменяемый release-tag/commit.
На VPS с небольшим свободным диском образ лучше доставлять уже собранным,
а не запускать тяжёлую сборку рядом с рабочими ботами.

## Настройки и ограничение доступа

Публичный образец — `.env.wordli.example`. Секреты размещают вне Git:
например, в `/etc/copilot/wordli.env`, владелец root, права `0600`.

| Переменная | Назначение |
|---|---|
| `APP_ENV=production` | Явный рабочий режим |
| `WORDLI_PUBLIC_ORIGIN` | Полный HTTPS-origin без пути |
| `WORDLI_BOT_TOKEN` | Токен только основного Copilot |
| `WORDLI_EXPECTED_BOT_ID` | Проверяемый числовой ID того же бота |
| `WORDLI_DATABASE_URL` | PostgreSQL URL отдельной непривилегированной роли |
| `WORDLI_ACCESS=restricted` | Первичная проверка только согласованными аккаунтами |
| `WORDLI_ALLOWED_USER_IDS` | Непустой список ID через запятую для restricted |
| `WORDLI_ACCESS=all` | Отдельно согласованное открытие всем подписанным Telegram-пользователям |
| `WORDLI_REMINDERS_ENABLED=false` | Отправка напоминаний выключена до явного согласования; `true` включает worker |

Даже `all` не отменяет проверку Telegram HMAC, возраста подписи и ID бота.
Ни токен, ни пароль БД, ни `initData` нельзя передавать в URL, выводить в
логи или добавлять в Git. Пароль внутри URL должен быть percent-encoded.

Production runtime проверяет схему и права до открытия порта. Он откажется
работать от SUPERUSER, от роли с созданием БД/ролей, REPLICATION/BYPASSRLS,
постоянным DDL или доступом к посторонним пользовательским таблицам.
Достаточны `SELECT`, `INSERT`, `UPDATE` трёх игровых таблиц; DELETE/TRUNCATE/
REFERENCES/TRIGGER не нужны. Существующие права `public` не ослабляются
и не переписываются автоматически ради прохождения проверки.

## Отдельная миграция — только после разрешения на релиз

1. Проверить рабочую БД, доступное место и сделать согласованную резервную
   копию. Проверить восстановление отдельно от рабочей БД.
2. Привилегированный оператор запускает `production_schema --apply`.
   Без `--apply` команда выполняет только проверку. Существующие игровые
   таблицы проверяются; несовместимая схема вызывает отказ, а не ALTER.
3. Оператор создаёт/проверяет роль `copilot_wordli` скриптом
   `database/migrations/002_wordli_runtime_role.sql`. Пароль новой роли
   передают через защищённое окружение `WORDLI_APP_PASSWORD`, не через
   аргументы команд или Git. Скрипт не меняет пароль уже существующей роли.
4. У runtime нет миграционного адреса и административного пароля.

При обновлении с первой версии сначала явно создать недостающую
`wordli_settings` командой миграции ниже, затем повторно выполнить
`002_wordli_runtime_role.sql` для минимальных прав новой таблицы.
Существующие профили, ходы и статистику не сбрасывать. Новый расчёт v2
выводится из сохранённой истории, без перезаписи результатов партий.
Без новой таблицы и прав сервер откажется стартовать, а не мигрирует молча.
Его собственная проверка подтверждает минимальность прав.

`WORDLI_MIGRATION_DATABASE_URL` хранится только в отдельном операторском
env-файле. Пример явного одноразового запуска уже подготовленного образа:

```bash
WORDLI_ENV_FILE=/etc/copilot/wordli-migration.env \
docker compose --env-file /etc/copilot/wordli-migration.env \
  -f docker-compose.wordli.yml run --rm --no-deps --entrypoint python \
  wordliapi -m prototypes.wordli.production_schema --apply
```

Перед выполнением оператор подтверждает точную целевую БД и выбранный
release-образ. Ограничение по таблицам не заменяет проверку правильности
выбранного PostgreSQL. При обновлении не подставлять тестовый env-файл
или базу вместо существующих production-настроек.

## Запуск после релизного разрешения

В Docker должна уже существовать сеть `bot_copilot_backend` основного
Copilot. Отдельный сервис игры подключается к ней и публикует HTTP только
на loopback VPS. `db`, `redis` и основной `bot` здесь не определены.

```bash
WORDLI_ENV_FILE=/etc/copilot/wordli.env \
docker compose --env-file /etc/copilot/wordli.env \
  -f docker-compose.wordli.yml up -d --no-deps wordliapi
```

Healthcheck подтверждает production-режим и реальное соединение с БД.
Внешняя проверка через HTTPS должна подтвердить валидный сертификат,
недоступность исходников/словаря/настроек и отказ неподписанному API-запросу.
Для первого запуска сначала проверяет владелец; `WORDLI_ACCESS=all`
включают отдельным решением. При последующих обновлениях сохраняют уже
согласованный режим доступа, не закрывая игру пользователям молча.
Меню основного бота включается отдельным `WORDLI_ENABLED=true` и рабочим
`WORDLI_WEBAPP_URL`; сам бот не перезапускают до разрешения на выкладку.

### HTTPS при последующих обновлениях

Постоянный origin — `https://copilot-games-v4956.duckdns.org`. Nginx и
сертификат Let's Encrypt подготовлены отдельно; известный путь сайта —
`/etc/nginx/sites-available/copilot-games-v4956`. Перед релизом проверяют
фактический конфиг, сертификат и продление, а не повторяют установку.

`/healthz` подтверждает только работу HTTPS-proxy. Готовность приложения
проверяется через `/api/health`: нужен HTTP 200, `ok=true`,
`mode=production` и реальная доступность БД. Первоначальная заглушка
«Игра готовится к запуску» — исторический этап, не текущий критерий.

`deployment/wordli/nginx-api.conf` — шаблон, а не команда перезаписи
рабочего сайта. Если origin и проксирование не меняются, обновление кода
не требует изменения Nginx. Если конфиг нужно поменять, сначала сохранить
его копию, выполнить `nginx -t` и только затем перечитать эту службу.
Игровой порт остаётся на `127.0.0.1:8770`; БД и Redis наружу не открываются.

## Тестовая production-сборка

`Dockerfile.wordli.test` добавляет pytest к изолированному игровому образу.
Выбранные независимые Wordli-тесты находятся в `qa_tests`; проектный
conftest, импортирующий aiogram с другим диапазоном aiohttp, не копируется.
Отдельная фикстура запрещает внешние HTTP и DNS-запросы.

Для проверки БД используется новый проект `wordli-production-review` из
`docker-compose.wordli.test.yml`, без host-портов и без подключения к
существующим контейнерам тестового или основного бота. PostgreSQL находится
в собственном tmpfs, база строго `copilot_review_test`. Две новые случайные
hex-строки задаются только в игнорируемом env-файле:

```text
WORDLI_QA_ADMIN_PASSWORD=NEW_RANDOM_HEX_FOR_THIS_TEST_ONLY
WORDLI_QA_APP_PASSWORD=ANOTHER_NEW_RANDOM_HEX_FOR_THIS_TEST_ONLY
```

```bash
docker build -f Dockerfile.wordli -t copilot-wordli:local .
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml build qa
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml up -d --wait db-test
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml run --rm --no-deps qa
```

Интеграционные тесты создают только собственные UUID-схемы. Отдельный тест
временно создаёт собственную UUID-роль: миграция выполняется оператором,
runtime имеет только игровой DML. Проверяются конкурентные устройства,
идемпотентность UUID, черновик, просрочки и исчерпание без повторов.
Очистка собственных тестовых объектов не затрагивает другие схемы/роли.

## Данные и откат

### Язык напоминаний

Приглашение и утреннее напоминание используют язык, выбранный в боте.
Для всех нерусских локалей добавляется отделённое пустой строкой предупреждение,
что игра пока доступна только на русском. Русским пользователям оно не показывается.
Кнопка возврата переводится вместе с напоминанием; `5БУКВ` и callback не меняются.
Расписание, согласие пользователя и защита от повторной доставки сохраняются.

Язык читается из `users.locale` непосредственно перед отправкой, а не из FSM
или языка интерфейса Telegram. Для будущего production-релиза владелец схемы
должен отдельно рассмотреть и проверить `004_wordli_reminder_locale.sql`:
игровой роли нужен только `select (user_id, locale)` на `users`, без доступа
к остальным колонкам и без записи в таблицу пользователей. Полный `select`
на таблицу выдавать нельзя. При недоступной таблице или правах сохраняется
русский резерв с безопасным предупреждением в логе; отправка не падает.
Каталоги переводов поставляются в образе через явный `COPY locales`.

Эта миграция только подготовлена в локальной ветке. На VPS она не применялась,
существующие production-права в рамках локальной разработки не изменяются.

### Обновление существующей игры

Сохранять все production-профили, ходы, черновики, ревизии и журнал UUID
`wordli_requests`; существующие `wordli_settings` также не сбрасывать.
При переходе с двух таблиц добавляется пустая `wordli_settings`, без
массового изменения истории. Новые настройки создаются по обращению
игрока с `reminder_enabled=false`; включение worker не включает подписку.
Существующие добровольные настройки напоминаний сохраняются.

При первоначальном запуске отдельно согласовывался перенос одного
профиля владельца. Это историческая одноразовая операция: при обновлениях
не повторять импорт и не начинать статистику заново. Тестовую SQLite,
синтетических участников и seed-скрипты из `.test-data` не переносить.

Очки v2 вычисляются из сохранённой истории. Число игр, исходы, попытки и
серии не сбрасываются; очки и позиции могут измениться из-за новых весов.

### Безопасный откат

1. Прекратить новые игровые запросы и остановить только игровой API с
   worker; другие боты и БД продолжают работать. Сделать свежий backup,
   особенно если новая версия уже принимала ходы или настройки.
2. До возврата к `f2e29b8` проверить совместимость всех историй на
   изолированной копии. Старый parser не принимает внутренние пробелы
   в позиционном черновике (`К ШКА`), а ведущие пробелы (`  КОТ`)
   удаляет, теряя позиции. Состав полей истории не менялся, но этого
   достаточно для отказа профиля или потери несданного ввода.
3. Если записи совместимы, вернуть прежний образ и настройки. Для старого
   API оператор отдельно отзывает у runtime-роли `SELECT/INSERT/UPDATE`
   на `wordli_settings`: лишний доступ блокирует старую проверку прав.
   Проверить старые `assert_schema` и `assert_runtime_permissions`.
   Саму таблицу, её данные и остальные минимальные права сохранить.
4. При несовместимости предпочесть режим обслуживания и исправление
   вперёд либо отдельно согласованный совместимый релиз. Не очищать
   историю, UUID-журнал или черновики автоматически ради старого образа.

После новых записей восстановление предрелизного backup может удалить
прогресс, платежи, пользователей и рецепты. Это не штатный откат и требует
отдельного разрешения с явным описанием возможной потери данных. Даже до
новых записей возврат кода обычно не требует восстановления всей БД.
Старый образ также возвращает формулу v1: сохранённые исходы остаются,
но очки могут отличаться. Журнал UUID не удалять ради пересчёта ответов.

Для повторного запуска новой версии вернуть минимальные права третьей
таблицы явным скриптом роли и снова проверить схему и полномочия.

Три замечания P2 последнего ревью приняты пользователем без исправления:
пограничная точность очков, редкий сетевой конфликт черновика и удаление
допустимого слова при цепочке трёх версий словаря. Эта подготовка не меняет
отложенные замечания и словарь. Новые согласованные веса формулы v2 и
позиционный ввод описаны в README; уже сохранённые исходы партий не меняются.
