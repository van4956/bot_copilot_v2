# Рабочий запуск Wordli

Этот документ описывает последующую выкладку. Он сам по себе не разрешает
merge, push, миграцию рабочей БД или перезапуск Copilot. Текущий этап —
подготовка в `branch-gpt-wordli` и отдельная настройка HTTPS.

## Разделение служб

```text
Telegram → https://copilot-games-v4956.duckdns.org
                         ↓ HTTPS proxy на VPS
                 127.0.0.1:8770 → wordliapi → PostgreSQL
```

- HTML/CSS/JS и API находятся на одном origin, без CORS и GitHub Pages.
- `production_server` — HTTP-сервер, а не второй polling основного бота.
- HTTPS-proxy управляется отдельно от приложения. Он не открывает порт БД.
- `docker-compose.wordli.yml` содержит только игру. Не объединять его
  запуск с безусловным `up`, `down` или `restart` всего основного Compose.
- В рабочей БД используются только `wordli_profiles` и `wordli_requests`.
  Таблицы `users`, `games`, `payments` и `cookbook` не меняются.
- В production нет автоматического DDL, seed или импорта тестовой SQLite.
- Тестовый entrypoint сохраняет прежние ограничения и не подходит для
  production. Не обходить их запуском рабочего бота с `APP_ENV=test`.

## Образ и зависимости

`Dockerfile.wordli` копирует только игровую папку и конфигурационный модуль,
не устанавливает aiogram, numpy и инструменты подготовки словаря.
`requirements-wordli.txt` отдельно фиксирует HTTP-зависимости, включая
`aiohttp==3.14.5`. Основной бот остаётся на собственном requirements.
Атрибуция, лицензии, готовый словарь и его архив находятся внутри образа.

До передачи образа проверяют отсутствие секретов и тестовых файлов,
сохраняют старый image ID, выбирают неизменяемый release-tag/commit.
На VPS с небольшим свободным диском образ лучше доставлять уже собранным,
а не запускать тяжёлую сборку рядом с рабочими ботами.

## Настройки и ограничение доступа

Публичный образец — `.env.wordli.example`. Секреты размещают вне Git:
например, в `/etc/copilot/wordli.env`, владелец root, права `0600`.

| Переменная | Назначение |
|---|---|
| `APP_ENV=production` | Явный рабочий режим |
| `WORDLI_PUBLIC_ORIGIN` | Полный HTTPS-origin без пути |
| `WORDLI_BOT_TOKEN` | Токен только основного Copilot |
| `WORDLI_EXPECTED_BOT_ID` | Проверяемый числовой ID того же бота |
| `WORDLI_DATABASE_URL` | PostgreSQL URL отдельной непривилегированной роли |
| `WORDLI_ACCESS=restricted` | Первичная проверка только согласованными аккаунтами |
| `WORDLI_ALLOWED_USER_IDS` | Непустой список ID через запятую для restricted |
| `WORDLI_ACCESS=all` | Отдельно согласованное открытие всем подписанным Telegram-пользователям |

Даже `all` не отменяет проверку Telegram HMAC, возраста подписи и ID бота.
Ни токен, ни пароль БД, ни `initData` нельзя передавать в URL, выводить в
логи или добавлять в Git. Пароль внутри URL должен быть percent-encoded.

Production runtime проверяет схему и права до открытия порта. Он откажется
работать от SUPERUSER, от роли с созданием БД/ролей, REPLICATION/BYPASSRLS,
постоянным DDL или доступом к посторонним пользовательским таблицам.
Достаточны `SELECT`, `INSERT`, `UPDATE` двух таблиц; DELETE/TRUNCATE/
REFERENCES/TRIGGER не нужны. Существующие права `public` не ослабляются
и не переписываются автоматически ради прохождения проверки.

## Отдельная миграция — только после разрешения на релиз

1. Проверить рабочую БД, доступное место и сделать согласованную резервную
   копию. Проверить восстановление отдельно от рабочей БД.
2. Привилегированный оператор запускает `production_schema --apply`.
   Без `--apply` команда выполняет только проверку. Существующие игровые
   таблицы проверяются; несовместимая схема вызывает отказ, а не ALTER.
3. Оператор создаёт/проверяет роль `copilot_wordli` скриптом
   `database/migrations/002_wordli_runtime_role.sql`. Пароль новой роли
   передают через защищённое окружение `WORDLI_APP_PASSWORD`, не через
   аргументы команд или Git. Скрипт не меняет пароль уже существующей роли.
4. У runtime нет миграционного адреса и административного пароля.
   Его собственная проверка подтверждает минимальность прав.

`WORDLI_MIGRATION_DATABASE_URL` хранится только в отдельном операторском
env-файле. Пример явного одноразового запуска уже подготовленного образа:

```bash
WORDLI_ENV_FILE=/etc/copilot/wordli-migration.env \
docker compose --env-file /etc/copilot/wordli-migration.env \
  -f docker-compose.wordli.yml run --rm --no-deps --entrypoint python \
  wordliapi -m prototypes.wordli.production_schema --apply
```

Это не команда текущего подготовительного этапа. Перед выполнением
оператор отдельно подтверждает точную целевую БД. Ограничение по таблицам
не заменяет проверку правильности выбранного PostgreSQL.

## Запуск после релизного разрешения

В Docker должна уже существовать сеть `bot_copilot_backend` основного
Copilot. Отдельный сервис игры подключается к ней и публикует HTTP только
на loopback VPS. `db`, `redis` и основной `bot` здесь не определены.

```bash
WORDLI_ENV_FILE=/etc/copilot/wordli.env \
docker compose --env-file /etc/copilot/wordli.env \
  -f docker-compose.wordli.yml up -d --no-deps wordliapi
```

Healthcheck подтверждает production-режим и реальное соединение с БД.
Внешняя проверка через HTTPS должна подтвердить валидный сертификат,
недоступность исходников/словаря/настроек и отказ неподписанному API-запросу.
Сначала проверяет владелец; `WORDLI_ACCESS=all` включают отдельным решением.
Меню основного бота включается отдельным `WORDLI_ENABLED=true` и рабочим
`WORDLI_WEBAPP_URL`; сам бот не перезапускают до разрешения на выкладку.

### Подготовленный HTTPS на VPS: состояние на 6 ноября 2026

Для `copilot-games-v4956.duckdns.org` отдельно установлен Nginx и получен
сертификат Let's Encrypt. Настройка сайта:
`/etc/nginx/sites-available/copilot-games-v4956`. Рабочий репозиторий VPS,
контейнеры ботов и БД при подготовке не менялись.

До релиза `/` показывает заглушку «Игра готовится к запуску», `/healthz`
подтверждает только работу HTTPS. `/api/health` намеренно возвращает 503:
рабочее приложение и его таблицы ещё не развёрнуты. Это не готовность игры.

HTTP-01 проверяется через `/var/www/copilot-games-v4956/acme`; таймер
`certbot.timer` включён. Пробное продление прошло, отдельный deploy-hook
перечитывает Nginx только для сертификата этой игры. DuckDNS API-токен
на сервер для этой схемы не передавался.

Готовый шаблон будущего проксирования — `deployment/wordli/nginx-api.conf`.
Он не применяется автоматически. После запуска и проверки `wordliapi`
нужно отдельно сохранить текущую заглушку, проверить новый конфиг через
`nginx -t` и только затем перечитать Nginx. Сам игровой порт остаётся
доступен только на `127.0.0.1:8770`; PostgreSQL и Redis наружу не открываются.

## Тестовая production-сборка

`Dockerfile.wordli.test` добавляет pytest к изолированному игровому образу.
Выбранные независимые Wordli-тесты находятся в `qa_tests`; проектный
conftest, импортирующий aiogram с другим диапазоном aiohttp, не копируется.
Отдельная фикстура запрещает внешние HTTP и DNS-запросы.

Для проверки БД используется новый проект `wordli-production-review` из
`docker-compose.wordli.test.yml`, без host-портов и без подключения к
существующим контейнерам тестового или основного бота. PostgreSQL находится
в собственном tmpfs, база строго `copilot_review_test`. Две новые случайные
hex-строки задаются только в игнорируемом env-файле:

```text
WORDLI_QA_ADMIN_PASSWORD=NEW_RANDOM_HEX_FOR_THIS_TEST_ONLY
WORDLI_QA_APP_PASSWORD=ANOTHER_NEW_RANDOM_HEX_FOR_THIS_TEST_ONLY
```

```bash
docker build -f Dockerfile.wordli -t copilot-wordli:local .
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml build qa
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml up -d --wait db-test
docker compose --env-file .test-data/wordli-production-review.env \
  -f docker-compose.wordli.test.yml run --rm --no-deps qa
```

Интеграционные тесты создают только собственные UUID-схемы. Отдельный тест
временно создаёт собственную UUID-роль: миграция выполняется оператором,
runtime имеет только игровой DML. Проверяются конкурентные устройства,
идемпотентность UUID, черновик, просрочки и исчерпание без повторов.
Очистка собственных тестовых объектов не затрагивает другие схемы/роли.

## Данные и откат

Рабочая игра начинается с пустой статистики для всех, кроме отдельного
согласованного переноса личного профиля владельца. Такой перенос выполняют
отдельно после backup и проверки словаря; в текущем entrypoint его нет.

При откате возвращают прежний образ/настройки Copilot и выключают только
новый API. Добавленные игровые таблицы оставляют, чтобы не потерять новые
партии. Полное восстановление всей БД — не штатный откат: оно может удалить
новые платежи, пользователей и рецепты.

Три замечания P2 последнего ревью приняты пользователем без исправления:
пограничная точность очков, редкий сетевой конфликт черновика и удаление
допустимого слова при цепочке трёх версий словаря. Эта подготовка не меняет
формулу, историю, словарь или соответствующую клиентскую логику.
